# Plan — besu-with-firefly

> **Owner:** Howin Ho · **Created:** 2026-10-01 · **Status:** Locked except items resolved by the Phase 0 spike
> *"Same Besu network, real FireFly process, a private token on Paladin, and numbers for what the gateway costs."*

---

## §1 Vision

**Long-term vision:** A personal reference stack showing how a multi-validator permissioned Besu network is provisioned and used through the real FireFly deploy and API process, with a Paladin private token beside a public ERC-3643 compliance token, and measured performance for each layer.

**Expansion axes:**
- **Width** — more Paladin domains (Zeto, Pente), FireFly multi-party with two members, more asset types
- **Depth** — ERC-3643 inside a Pente privacy group, Paladin operations in the CLI, persistent volumes, real authentication and key management

**v1 wedge:** A 4-validator QBFT Besu network (`f=1`) with 2 RPC nodes; FireFly (gateway mode) deploying and serving the official ERC-3643 `COIN`; a Paladin Noto private token; a Python CLI over FireFly; Caliper results for chain layer vs FireFly layer. Nothing beyond this is in v1.

Not applicable — no planned expansion axes that need a generic data model (CLAUDE.md §2: no abstractions for one-off use). The only naming rule: the earlier project's `mock-middleware` is not used or named in this repo's code.

## §4 Phase Plan

Timelines are rough estimates for a solo developer, not commitments.

### Phase 0 — Spike (about 3–5 days)

**Goal**: Know, with evidence, whether each risky assumption holds, and what the fallback is if not.

**Scope**:
- A throwaway minimal Compose: 1 Besu node, FireFly, Paladin
- A written results note
- Out of scope: the 4-validator network, the CLI, any benchmark numbers

**Steps**:

1. Start a single Besu node on a QBFT-style genesis with `zeroBaseFee`; attach FireFly (hand-written Compose, gateway mode) to it; send one write through `evmconnect`.
   > **Gate ✓** — a FireFly contract invoke returns a succeeded operation, and `eth_getTransactionReceipt` shows the transaction mined

2. Deploy a small contract through FireFly's deploy API, then the largest T-REX contract (Token).
   > **Gate ✓** — both deployments succeed; the Token's deployed bytecode size is recorded and is under 24 576 bytes (or the shortfall is documented)

3. Start one Paladin node from `lfdecentralizedtrust/paladin:v1.0.0` with hand-written config pointed at the Besu node; deploy a Noto token.
   > **Gate ✓** — Paladin reports healthy and a Noto mint transaction completes

4. Record the EVM version Paladin's and FireFly's contracts need.
   > **Gate ✓** — D-08 is confirmed or revised in this file

5. Install Caliper with its Besu connector and run one trivial round against the Besu node.
   > **Gate ✓** — Caliper writes a report; Node and Caliper versions are recorded

6. Write `docs/spike-results.md`.
   > **Gate ✓** — one section per risk (D-15 ①–④), each marked feasible / not feasible with a fallback

**Exit gate**:
- [ ] `docs/spike-results.md` exists with all four sections answered
- [ ] D-03, D-08, D-09 are updated if any result requires it
- [ ] Image and tool versions to pin are listed
- [ ] The developer has signed off

**Anti-gate**: do not start Phase 1 until every risk has a feasible path or a chosen fallback. If FireFly cannot attach to an external Besu at all, stop and re-plan (D-02 is then in question).

---

### Phase 1 — Network (about 2–3 days)

**Goal**: The 4-validator QBFT Besu network with 2 RPC nodes, zero-gas, generated from scripts.

**Scope**:
- Genesis, key and `static-nodes.json` generator; Compose for validators and RPC nodes
- Out of scope: FireFly, Paladin, contracts, CLI

Phase 1 is sliced horizontally by layer, not by vertical slice (see rationale below).

#### M1.1 — Genesis and keys (Day 1)

**Services in scope**: generator script only
**Out**: any running container
**Surface for demo**: the generated files on disk
**Vertical slice proven**: a valid 4-validator QBFT genesis exists that all validators can boot from

**Steps**:

1. Write the generator around `besu operator generate-blockchain-config` (chainId `20260916`, `blockperiodseconds` 2, `requesttimeoutseconds` 4, empty `alloc`, fork level per D-08).
   > **Gate ✓** — `genesis.json` contains a `qbft` block and 4 validator addresses in `extraData`; 4 key files exist

2. Generate `static-nodes.json` and the `admin`/`anson`/`beatrice` wallet keys.
   > **Gate ✓** — `static-nodes.json` lists 4 enodes; wallet keys exist

**Exit gate**:
- [ ] Running the generator twice from scratch produces a consistent, valid set
- [ ] `docker compose config` exits 0

#### M1.2 — Validators and fault tolerance (Day 1–2)

**Services in scope**: `besu-validator-1..4`
**Out**: RPC nodes, everything above Besu
**Surface for demo**: `docker compose logs besu-validator-1`
**Vertical slice proven**: the validator set produces blocks and survives one failure

**Steps**:

1. Define the four validators in Compose, peered via `static-nodes.json`.
   > **Gate ✓** — all 4 healthy, peer count ≥ 3 in each log, no restart loop

2. Stop one validator.
   > **Gate ✓** — block height continues to increase within 30s; the validator rejoins on restart

**Exit gate**:
- [ ] Killing any single validator does not halt block production

#### M1.3 — RPC nodes and consistency (Day 2–3)

**Services in scope**: `besu-rpc-anson`, `besu-rpc-beatrice`
**Out**: FireFly, Paladin
**Surface for demo**: `curl` to `:8545` and `:8555`
**Vertical slice proven**: two RPC endpoints expose identical chain state

**Steps**:

1. Add both RPC nodes as non-validating nodes (no validator key), peered to all 4 validators.
   > **Gate ✓** — both `running` in `docker compose ps`

2. Check consistency and gas.
   > **Gate ✓** — `eth_blockNumber` agrees within 1 block 5s apart; `eth_gasPrice` is `0x0` on both

**Exit gate (= Phase 1 exit gate)**:
- [ ] 4 validators healthy and tolerant of 1 failure
- [ ] 2 RPC nodes consistent
- [ ] `pytest -m integration` network tests pass

**Anti-gate**: if killing 1 of 4 validators halts the chain, stop and re-check `extraData` against the validator keys. Do not proceed.

**Rationale for this slicing:** horizontal layers (keys → validators → RPC) because each layer is a hard dependency for the next, there is no stakeholder needing a vertical demo, and FireFly and Paladin cannot be attached until the network exists.

### Phase 2 — FireFly + ERC-3643 (about 5–8 days)

**Goal**: `COIN` deployed through FireFly and usable through the contract API, with compliance enforced on-chain.

**Scope**:
- FireFly gateway mode; T-REX compile config; deploy, interface and API registration; onboarding and transfer
- Out of scope: Paladin, CLI, Caliper

**Steps**:

1. Add FireFly (core, evmconnect, signer, Postgres) to Compose with keys `admin`/`anson`/`beatrice`.
   > **Gate ✓** — `GET /api/v1/status` reports ready; `make up` needs no manual steps

2. Compile the T-REX suite with the EVM target from the spike.
   > **Gate ✓** — compile exits 0; each contract's deployed size is under the limit

3. Deploy every contract through FireFly's deploy API.
   > **Gate ✓** — `deployed-addresses.json` has only non-zero addresses and each has code on-chain; token reads back `Coin`/`COIN`

4. Register contract interfaces and APIs for `COIN` and the IdentityRegistry.
   > **Gate ✓** — a read (`balanceOf`) and a write (`mint`) both succeed through the generated API

5. Onboard Admin/Anson/Beatrice and transfer.
   > **Gate ✓** — Anson holds 1000, Beatrice 0, both verified; Anson → Beatrice transfer succeeds

6. Compliance rejection.
   > **Gate ✓** — transfer to an unverified address reverts via the contract API directly, balances unchanged

7. Reset repeatability.
   > **Gate ✓** — `make reset && make up && make deploy` leaves a working `COIN`

**Exit gate**:
- [ ] Integration tests (onboarding, transfer, rejection) pass
- [ ] Re-running register or claim sends no redundant transaction
- [ ] Reset repeatability proven

**Anti-gate**: do not proceed to Phase 3 if the compliance-rejection test does not actually revert, because the core guarantee would not be real.

---

### Phase 3 — Paladin + Noto (about 4–6 days)

**Goal**: A Noto private token on the same Besu network.

**Scope**:
- Two Paladin nodes, a notary, Paladin DB; Noto deploy; mint and transfer
- Out of scope: Zeto, Pente, CLI support

**Steps**:

1. Add Paladin nodes and the notary to Compose with the spike's hand-written config.
   > **Gate ✓** — all report healthy and reach `besu-rpc-*`

2. Deploy a Noto token.
   > **Gate ✓** — token address returned and queryable from each party's node

3. Admin mints to Anson; Anson transfers to Beatrice.
   > **Gate ✓** — Beatrice's node shows the received balance

4. Check privacy.
   > **Gate ✓** — a Paladin node that is not a party does not see the transfer; the public chain shows no amounts or parties

5. Extend `make reset` to clear the Paladin DB.
   > **Gate ✓** — after reset, Paladin starts clean against a fresh chain

**Exit gate**:
- [ ] Noto integration tests pass
- [ ] `make reset` clears all three stores

**Anti-gate**: if Paladin cannot run from hand-written config on Compose, fall back to Paladin on `kind` (not Paladin's own devnet Besu) before continuing; record the change in D-09.

### Phase 4 — Python CLI (about 3–5 days)

**Goal**: A small CLI over FireFly with logic in `src/core/`.

**Scope**:
- `core`, FireFly adapter, CLI adapter; four commands; unit and integration tests
- Out of scope: Paladin commands, web UI

**Steps**:

1. Define the port and onboarding/transfer logic in `src/core/`.
   > **Gate ✓** — unit tests with a mocked port pass; `src/core/` contains no `print`, `input` or network call

2. Implement the FireFly adapter.
   > **Gate ✓** — adapter tests pass against recorded or mocked FireFly responses

3. Implement the CLI commands.
   > **Gate ✓** — each command runs against the live stack and its output is asserted in an integration test

4. Handle pending and unknown states.
   > **Gate ✓** — a test proves the CLI never reports success from pending/unknown

**Exit gate**:
- [ ] `ruff check .`, `mypy .`, `pytest` all pass
- [ ] Integration tests pass across 3 consecutive fresh-stack runs

**Anti-gate**: do not call Phase 4 done with a flaky integration test; fix the cause.

---

### Phase 5 — Caliper (about 3–5 days)

**Goal**: Measured chain-layer and FireFly-layer performance, and the difference.

**Scope**:
- `perf/` sub-project, wallet setup, two rounds, results note
- Out of scope: Paladin benchmarks, tuning Besu for throughput

**Steps**:

1. Create `perf/` and the Caliper network config for `besu-rpc-*`.
   > **Gate ✓** — a trivial round runs and writes a report

2. Write the wallet setup (N verified wallets with `COIN`).
   > **Gate ✓** — N wallets verified on-chain; N is configurable

3. Chain-layer round: `Token.transfer` direct over RPC.
   > **Gate ✓** — report with TPS and latency

4. FireFly-layer round: same transfer through FireFly's contract API.
   > **Gate ✓** — report with TPS and latency

5. Write the results note.
   > **Gate ✓** — both result sets, the difference, the genesis settings (block period, gas limit) and the caveat that results describe this demo configuration

**Exit gate**:
- [ ] Both rounds reproducible from a fresh `make reset && make up && make deploy`
- [ ] Results note committed

**Anti-gate**: do not publish numbers without the configuration they were measured under.

## §5 Architecture Snapshot

**Topology:** one Compose stack: 4 QBFT validators + 2 RPC nodes → FireFly (gateway, signs for `COIN`) and Paladin (Noto) → Python CLI and Caliper on the host. Detail: `docs/architecture.md`.

| Phase gate | Architecture change |
|---|---|
| Phase 0 → 1 | Spike results fix image versions, EVM fork, Paladin config shape and Node version |
| Phase 1 → 2 | FireFly is introduced as the sole signer for `COIN` traffic; it is a hard dependency from here |
| Phase 2 → 3 | Paladin is introduced as a second, independent path to the chain; it shares Besu but not FireFly |
| Phase 3 → 4 | `src/core/` and the FireFly adapter are the first custom code in the project |
| Phase 4 → 5 | `perf/` adds a Node toolchain beside Python |

## §6 KPI Summary

**North Star:** a transfer of `COIN` completes through FireFly and a Noto transfer completes through Paladin, both on the same 4-validator network, with chain-layer and FireFly-layer numbers measured.

| Phase | Gating metric | Target |
|---|---|---|
| 0 | Risks resolved | 4/4 with a written result and fallback |
| 1 | Fault tolerance and consistency | Chain survives 1-of-4 validators down; RPC nodes within 1 block |
| 2 | Deploy and compliance | `COIN` deployed through FireFly; rejection test passes 100% of runs |
| 3 | Privacy | Non-party node never sees the Noto transfer |
| 4 | Test stability | All tests green across 3 consecutive fresh-stack runs |
| 5 | Performance data | Chain-layer and FireFly-layer TPS and latency recorded with configuration |

**Anti-metric kill switch:**
- If FireFly cannot attach to an external Besu (Phase 0), stop and re-plan; D-02 is in question.
- If the compliance-rejection test cannot be made to revert after about a day of debugging (Phase 2), re-check the T-REX wiring before continuing.
- If Paladin cannot connect to the shared Besu network by any route (Phase 3), drop Paladin to a post-MVP item rather than splitting it onto its own chain.

## §8 Compliance Notes

- **CASL:** Not applicable. No messaging is sent.
- **PIPEDA / provincial privacy (Canada):** Not applicable. No real personal data is collected, stored or processed. Anson, Beatrice and Admin are fictional. All data stays on the developer's machine, so no data residency requirement, accountable person or breach notification applies.
- **GDPR / HIPAA / PCI / other:** Not applicable. No EU data subjects, health data or card data.
- **Securities and KYC:** `COIN` and the T-REX setup are a learning exercise. Claims are self-issued by the Admin; this is not audit-grade compliance tooling and is not KYC/AML.
- This position (D-11) must be re-evaluated from scratch in a new `/grill-me` pass before any of this is reused with real data.
